# AUTO LANDMARK ARCHITECTURE

**Project:** Morphology Pipeline
**Document version:** 1.0
**Status:** architecture specification
**Purpose:** define the modular architecture for staged automatic landmark placement, human review, retraining, model evaluation, and safe application to the remaining dataset.

---

# 1. Purpose

The auto-landmark subsystem must support an iterative workflow in which a human initially annotates a relatively small number of images, trains a model, lets the model predict landmarks on a selected number of additional images, reviews/corrects those predictions, retrains the model, and repeats the cycle until quality is sufficient.

The system must also allow the current trained model to be applied to all remaining unannotated images.

Primary workflow:

```text
Manual annotation
        ↓
Train model
        ↓
Model v001
        ↓
Predict N images
        ↓
Human review/correction
        ↓
Add reviewed images to training pool
        ↓
Retrain
        ↓
Model v002
        ↓
Predict next N images
        ↓
...
        ↓
Quality acceptable
        ↓
Predict all remaining images
```

The number `N` must be selected by the user and must not be hard-coded.

Examples:

```text
30–50 manually annotated images
↓
train
↓
predict 10
↓
review/correct
↓
retrain
↓
predict 20
↓
review/correct
↓
retrain
↓
predict 50
↓
...
```

The software must not require these exact numbers. They are only examples of intended usage.

---

# 2. Core architectural rule

The following components must remain logically separate:

```text
GUI
Dataset management
Training
Inference
Evaluation
Model registry
Quality control
```

The GUI must not contain model-training logic.

The training module must not contain GUI logic.

The inference module must not decide which images belong to the training set.

The evaluation module must not modify annotations.

The model must be replaceable later without requiring a redesign of the annotation GUI or the project data format.

Conceptually:

```text
                 ┌───────────────┐
                 │      GUI      │
                 └───────┬───────┘
                         │
                 Dataset Manager
                /        │        \
               /         │         \
          Training   Inference   Evaluation
             │           │           │
             ↓           ↓           ↓
         Model Registry Predictions Metrics
```

---

# 3. Scope of version 1

Version 1 must provide only the functionality necessary for a reliable iterative annotation workflow.

Required:

* manual landmark annotations;
* dataset status tracking;
* training-data snapshots;
* model versioning;
* model training;
* inference on selected images;
* inference on all remaining images;
* human review of predicted points;
* preservation of prediction provenance;
* evaluation on a fixed validation set;
* landmark-specific error statistics;
* model-level quality statistics;
* basic geometry/sanity checks;
* rollback to an older model.

Not required in version 1:

* ensembles;
* cloud services;
* distributed training;
* PostgreSQL or other external database servers;
* automatic hyperparameter sweeps;
* multiple competing neural-network architectures;
* LLM integration;
* complex active-learning algorithms;
* automatic model replacement without human confirmation.

Keep the first implementation simple, modular, inspectable, and reversible.

---

# 4. Image states

Every image used by the project must have exactly one primary annotation state.

Required states:

```text
UNLABELED
MANUAL
PREDICTED
REVIEWED
EXCLUDED
```

Meaning:

## UNLABELED

No valid landmark annotation exists.

The image can be selected for automatic prediction.

---

## MANUAL

Landmarks were placed manually by the operator.

The image is eligible for model training.

---

## PREDICTED

Landmarks were generated by a model but have not yet been approved by a human.

The image must NOT be used for training.

---

## REVIEWED

Model predictions were inspected by the operator and either accepted or corrected.

The image is eligible for model training.

---

## EXCLUDED

The image must not participate in training or automatic annotation.

Examples may include unsuitable photographs, strongly curved specimens, damaged fish, unusable orientation, or other operator-defined reasons.

The exact exclusion reason should be stored separately.

---

# 5. Strict training rule

Only the following image states may enter the training dataset:

```text
MANUAL
REVIEWED
```

The following states must never enter training automatically:

```text
UNLABELED
PREDICTED
EXCLUDED
```

This is a hard safety requirement.

The model must never be trained on its own unchecked predictions.

---

# 6. Landmark provenance

For every individual landmark coordinate, the system must preserve its origin.

Required provenance values:

```text
manual
predicted
corrected
```

Meaning:

## manual

The operator placed the point manually without an existing model prediction.

## predicted

The model predicted the point and the operator accepted its position without moving it.

## corrected

The model predicted the point, but the operator changed its position.

Example:

```text
image_001

SnT       predicted
EyeC      corrected
DorsalO   predicted
CPminD    corrected
```

This information must not be discarded after review.

It is required for later calculation of landmark-specific failure rates.

---

# 7. Prediction metadata

Every automatically generated annotation must preserve at minimum:

```text
model_id
prediction_timestamp
point coordinates
point confidence, if supported by model
original predicted coordinates
review status
```

If the operator moves a predicted point, the original prediction must remain recoverable for evaluation.

Example conceptual record:

```text
landmark_id: 7
predicted_x: 1432.5
predicted_y: 812.4
final_x: 1441.1
final_y: 806.8
source: corrected
model_id: model_004
```

Do not overwrite the original prediction with the corrected coordinate.

---

# 8. Dataset Manager

Dataset management must be implemented as a separate module.

Its responsibilities are:

* determine the status of every image;
* determine which images are eligible for training;
* determine which images are eligible for prediction;
* maintain exclusions;
* maintain annotation provenance;
* create training snapshots;
* create or maintain validation assignments;
* provide counts to the GUI.

Typical queries should conceptually include:

```text
get_training_images()
get_unlabeled_images()
get_predicted_images()
get_reviewed_images()
get_excluded_images()
```

The GUI should request information from the Dataset Manager instead of reproducing dataset-selection logic itself.

---

# 9. Training snapshot

Every training run must use an immutable snapshot of the data that existed when training started.

Example:

```text
training_runs/
    training_run_001/
    training_run_002/
    training_run_003/
```

Each run must record:

```text
run_id
creation time
list of training images
list of validation images
number of training images
number of landmarks
landmark definition/version
crop/preprocessing configuration
training parameters
software/model configuration
resulting model_id
```

A future inspection must make it possible to answer:

> Exactly which annotations were used to produce model_005?

The answer must not depend on reconstructing the state of the current dataset.

---

# 10. Validation set

Model quality must not be estimated from the same images used for training.

A validation subset must therefore be maintained separately.

Preferred behavior:

1. create a validation subset once when sufficient manually verified data are available;
2. keep this validation subset stable across successive training runs;
3. compare model versions on the same validation images whenever possible.

Conceptually:

```text
TRAIN
VALIDATION
```

An image in the validation set must not simultaneously be used for training in the same evaluation run.

The validation assignment must be stored persistently.

Changing the validation set must be an explicit action and must be recorded.

---

# 11. Training module

Training must be exposed through a small, stable interface.

Conceptually:

```python
train(training_snapshot, config) -> training_result
```

The exact implementation may differ, but other application modules must not depend directly on the internal neural-network code.

Training output must include:

```text
model_id
model files
training configuration
training log
training metrics
validation metrics
training snapshot reference
success/failure state
```

Training errors must not silently replace the active model.

A newly trained model should become active only after successful completion and creation of its required metadata.

---

# 12. Model Registry

All model versions must be preserved.

Recommended structure:

```text
models/
    model_001/
        model.*
        config.json
        metrics.json
        training_manifest.csv
        training_log.txt

    model_002/
        model.*
        config.json
        metrics.json
        training_manifest.csv
        training_log.txt
```

And a registry:

```text
models/
    model_registry.json
```

Each registered model should contain at minimum:

```text
model_id
created_at
training_run_id
training_image_count
validation_image_count
validation_metrics
status
```

Possible statuses:

```text
active
inactive
failed
archived
```

Only one model should normally be marked `active`.

Older successful models must not be deleted or overwritten automatically.

The GUI should allow the active model to be identified clearly.

Rollback must be possible.

Example:

```text
Current model: model_007
```

with the ability to activate:

```text
model_006
```

without retraining.

---

# 13. Inference module

Inference must be independent from training and GUI code.

Conceptual interface:

```python
predict(image, model_id) -> prediction
```

or for batch processing:

```python
predict_batch(images, model_id) -> predictions
```

Each prediction should contain:

```text
image identifier
model identifier
landmark identifiers
x coordinates
y coordinates
confidence values if available
prediction timestamp
```

The inference module must not decide whether predictions are accepted.

It must not convert `PREDICTED` into `REVIEWED`.

Only human review may do that.

---

# 14. Predict N workflow

The GUI must provide a command equivalent to:

```text
Predict N images
```

The user selects a number, for example:

```text
10
20
50
100
custom value
```

Only eligible `UNLABELED` images should be selected.

Existing:

```text
MANUAL
REVIEWED
PREDICTED
EXCLUDED
```

images must not be overwritten by a normal batch prediction command.

After successful prediction:

```text
UNLABELED → PREDICTED
```

---

# 15. Predict all remaining

The GUI must also provide:

```text
Predict all remaining
```

This must process only eligible `UNLABELED` images.

It must not modify manually or previously reviewed annotations.

Before a large batch begins, the software should clearly identify:

```text
active model
number of images to process
```

The operation must create a log.

Interrupted processing should be recoverable without requiring already completed images to be recomputed unnecessarily.

---

# 16. Review workflow

A dedicated review mode must be available for images with:

```text
PREDICTED
```

status.

The operator must be able to:

* inspect predicted landmarks;
* move incorrect landmarks;
* delete/re-add landmarks if necessary;
* accept all points;
* exclude the image;
* move to the next predicted image.

When review is finished:

```text
PREDICTED → REVIEWED
```

For every point:

* unchanged prediction → `predicted`;
* moved/replaced prediction → `corrected`.

The original model prediction must remain stored.

---

# 17. Human correction statistics

The system should be able to calculate:

```text
number of reviewed images
number of fully accepted images
number of images requiring correction
number of corrected landmarks
correction rate by landmark
```

Example:

```text
Reviewed predictions: 100

Images accepted without correction: 82
Images requiring correction: 18

SnT corrected: 2 %
EyeC corrected: 5 %
CPminD corrected: 17 %
```

These statistics are descriptive and must not replace geometric error measurements.

---

# 18. Evaluation module

Evaluation must be independent from training and inference.

Conceptual interface:

```python
evaluate(model_id, validation_dataset) -> metrics
```

The module must compare predicted coordinates against verified human coordinates.

At minimum, metrics must be calculated:

* globally;
* per landmark;
* per image where useful.

---

# 19. Error calculation

Raw pixel error must be available for diagnostics but must not be the primary scientific quality metric.

For landmark `i`:

```text
pixel_error_i =
sqrt(
    (x_pred - x_true)^2 +
    (y_pred - y_true)^2
)
```

The main normalized error must divide spatial error by a reproducible measure of specimen/image scale.

Conceptually:

```text
normalized_error =
landmark_error / reference_length
```

The exact reference length must be defined once and stored in project configuration.

Potential reference measures can include a stable body-length proxy defined by the project.

Do not silently change the normalization definition between model versions.

The normalized metric should be displayable as percentage:

```text
normalized_error × 100
```

Example:

```text
0.0063
=
0.63 %
```

If physical calibration is available, optional error in millimetres may also be calculated.

Possible displayed values:

```text
pixels
mm
% reference body length
```

---

# 20. Required model-level metrics

At minimum calculate and preserve:

```text
median normalized error
mean normalized error
90th percentile normalized error
95th percentile normalized error
maximum error
```

Per-landmark metrics should include at minimum:

```text
median error
90th percentile error
sample count
```

Do not rely on a single average value.

---

# 21. Human repeatability baseline

The system architecture must support evaluation of operator repeatability.

A subset of images may be annotated independently by the same operator on two separate occasions.

These data must allow calculation of:

```text
Human ↔ Human error
```

The model can then be compared against:

```text
AI ↔ Human error
```

The software should keep these concepts separate.

Do not automatically claim that AI is equivalent to a human merely because values appear similar.

The software should report the measured values and leave interpretation to the researcher.

---

# 22. Human-baseline dataset

Human repeatability annotations must not overwrite the normal annotation set.

They should be stored as separate annotation sessions or equivalent records.

Conceptually:

```text
human_repeatability/
    session_1
    session_2
```

The same image must therefore be capable of having more than one independently stored human annotation for this specific evaluation purpose.

This feature may be implemented after the basic prediction/review loop, but the architecture must not make it impossible.

---

# 23. Confidence

If the model provides a confidence value, confidence must be stored separately from measured accuracy.

A high confidence value must never be interpreted automatically as proof that a landmark is correct.

Confidence may be used for:

* sorting suspicious predictions;
* prioritizing images for review;
* future active-learning selection.

Scientific model quality must be based on comparison against verified annotations.

---

# 24. Basic active learning

Initial implementation should remain simple.

Two selection modes are desirable:

```text
Predict next N
Predict N most uncertain
```

`Predict next N` selects normal eligible unlabeled images.

`Predict N most uncertain` may later use model confidence or another clearly defined uncertainty measure.

Do not implement complex active-learning algorithms until the standard iterative workflow is stable.

---

# 25. Geometry / sanity checker

A lightweight rule-based sanity checker must be a separate component from the neural network.

Purpose:

detect obviously implausible prediction geometry.

Possible checks may include:

* landmark outside allowed image/specimen region;
* impossible landmark order;
* two landmarks accidentally swapped;
* landmarks unrealistically close together;
* landmark relationships violating known project geometry.

The checker must not silently modify coordinates.

It should produce flags such as:

```text
OK
REVIEW_REQUIRED
```

and explanatory reasons.

Example:

```text
REVIEW_REQUIRED:
landmark order violation between point 7 and point 8
```

Rules must be explicit and configurable.

Do not add biological geometry assumptions unless they are deliberately defined for this landmark scheme.

---

# 26. Quality panel in GUI

The GUI should eventually contain a compact read-only quality panel.

Example:

```text
AUTO LANDMARK QUALITY

Active model: model_007
Training images: 146
Validation images: 30

Median error: 0.63 %
90th percentile: 1.21 %

Human repeatability: 0.48 %

Reviewed predictions: 94
Accepted unchanged: 81 %
Corrected: 19 %
```

And optionally:

```text
LANDMARKS NEEDING MOST ATTENTION

CPminV     1.70 %
DorsalI    1.40 %
EyeP       1.20 %
```

The panel must read already calculated metrics.

The GUI must not contain its own independent metric calculations.

---

# 27. Dataset and annotation persistence

Persistent records must contain enough information to reconstruct:

* image identity;
* image status;
* crop identity/configuration;
* landmark coordinates;
* landmark names/numbers;
* provenance of each point;
* prediction model;
* original predicted coordinates;
* reviewed coordinates;
* exclusion state/reason;
* validation membership;
* relevant timestamps.

Existing project data formats should be reused where practical.

Do not create a second independent source of truth for the same annotation data unless necessary.

If schema changes are required, migration must be explicit and backward-safe.

Before changing an existing annotation file format, inspect the current project implementation.

---

# 28. Landmark definition version

The system must store which landmark scheme was used.

Example:

```text
landmark_schema_version: 1
```

Changing landmark numbers, meanings, or order in the future must create a new schema version.

Old models must remain associated with the landmark scheme on which they were trained.

A model trained for one landmark schema must not silently run against an incompatible schema.

---

# 29. Crop and coordinate consistency

Training, inference, display, and evaluation must use a consistent coordinate system.

The implementation must explicitly define whether model coordinates refer to:

```text
original image
crop
resized model input
normalized coordinates
```

Conversions must occur in one clearly defined place.

The GUI should ultimately receive coordinates in the same coordinate space used by its annotation layer.

Do not duplicate coordinate-conversion logic across modules.

Loss of coordinate precision through repeated conversions should be avoided.

---

# 30. Reproducibility

Every completed training run must preserve sufficient metadata to reproduce or audit it later.

At minimum:

```text
training data manifest
validation data manifest
landmark schema version
model configuration
preprocessing configuration
training parameters
software/model version where practical
random seed where used
result metrics
```

Exact byte-identical reproducibility is not required if the underlying ML framework is nondeterministic, but the input data and configuration must be recoverable.

---

# 31. Logs

Training, prediction, review-state transitions, and evaluation must produce useful logs.

Logs should record:

```text
timestamp
operation
model_id where applicable
image count
success/failure
error details
```

Batch operations must not fail silently.

A failed item should be identifiable.

---

# 32. Failure safety

The following operations must be safe against partial failure:

```text
training
batch prediction
metric generation
model activation
```

General rules:

* do not overwrite the previous good model;
* do not mark an image as successfully predicted before prediction data are safely stored;
* do not activate a failed or incomplete model;
* preserve logs for failed operations;
* allow retry where practical.

---

# 33. No destructive overwriting

Automatic inference must not overwrite manually verified coordinates by default.

Automatic prediction on an image with state:

```text
MANUAL
REVIEWED
```

must require an explicit special action if ever supported.

Normal `Predict N` and `Predict all remaining` must skip them.

---

# 34. Model activation

Training a new model and activating a model are logically separate actions.

Default behavior may activate a successfully trained model, but only after all required files and metadata are safely written.

A previous active model must remain available.

Registry state should make activation explicit.

---

# 35. Suggested module boundaries

Exact filenames may be adapted to the existing repository after inspection, but responsibilities should correspond approximately to:

```text
auto_landmark/
    dataset_manager.py
    training.py
    inference.py
    evaluation.py
    model_registry.py
    sanity_checks.py
    types.py
```

Possible additional modules later:

```text
active_learning.py
human_repeatability.py
```

Do not create these exact files merely to satisfy this document if the existing project already has an appropriate modular structure.

Prefer integration with existing architecture over unnecessary duplication.

The architectural separation of responsibilities is mandatory; exact filenames are not.

# 36. Stable service interfaces

The rest of the application should communicate with the auto-landmark subsystem through a small interface.

Conceptually:

```python
train(...)
predict(...)
predict_batch(...)
evaluate(...)
get_active_model(...)
set_active_model(...)
```

Dataset operations should similarly expose explicit functions instead of requiring GUI code to inspect low-level files everywhere.

Do not allow GUI widgets to become the primary API.

# 37. GUI behavior

The GUI should eventually expose approximately:

```text
Train model

Predict...
    next N
    most uncertain N
    all remaining

Review predictions

Model:
    current model
    previous models
    activate selected model

Quality
```

Exact visual design may follow the current application.

Do not redesign unrelated GUI areas merely to implement auto-landmarking.

---

# 38. Training button behavior

When the user selects:

```text
Train model
```

the application should approximately:

1. query Dataset Manager for eligible annotations;
2. verify minimum structural requirements;
3. create a training snapshot;
4. start training;
5. save logs;
6. evaluate the resulting model;
7. register the model;
8. activate it only if training completed correctly;
9. update GUI status.

The GUI must clearly report failure if any critical stage fails.

---

# 39. Review button behavior

`Review predictions` should prioritize images currently in:

```text
PREDICTED
```

state.

The review workflow should minimize operator actions.

Expected common case:

```text
open image
inspect points
correct only if needed
accept
next image
```

The system should make it possible to review many predictions efficiently.

---

# 40. Quality progression

The application should preserve enough information to compare model versions over time.

Example:

```text
model_001    median error 1.80 %
model_002    median error 1.21 %
model_003    median error 0.82 %
model_004    median error 0.71 %
```

Only metrics calculated on comparable validation data should be directly compared.

If validation data changed, this must be visible in the metadata.

---

# 41. Do not automatically decide when model quality is “good enough”

The application may display metrics and warnings.

It must not initially impose an arbitrary hard threshold such as:

```text
model ready if error < X %
```

unless such a threshold is later scientifically justified and explicitly configured.

The final decision to apply a model to all remaining images belongs to the user.

---

# 42. Development stages

Implementation must proceed incrementally.

Recommended order:

## Stage 1 — data state foundation

Implement/verify:

```text
UNLABELED
MANUAL
PREDICTED
REVIEWED
EXCLUDED
```

and dataset-state persistence.

No neural network integration is required yet.

---

## Stage 2 — annotation provenance

Preserve:

```text
manual
predicted
corrected
```

and original prediction coordinates.

---

## Stage 3 — model registry

Implement model directories, metadata, active-model selection, and rollback.

No GUI redesign.

---

## Stage 4 — training API

Implement a standalone training service using verified training data.

It must be callable independently of GUI widgets.

---

## Stage 5 — inference API

Implement prediction for one image and batches.

Verify coordinate conversion independently.

---

## Stage 6 — GUI Train integration

Connect the existing GUI to the training service.

---

## Stage 7 — Predict N

Add user-selectable batch size and inference on eligible `UNLABELED` images.

---

## Stage 8 — review workflow

Implement:

```text
PREDICTED → REVIEWED
```

with accepted/corrected provenance.

---

## Stage 9 — evaluation

Add fixed-validation evaluation and per-landmark metrics.

---

## Stage 10 — quality panel

Display stored model and review statistics in GUI.

---

## Stage 11 — predict all remaining

Enable large-batch inference only after the smaller iterative cycle is reliable.

---

## Stage 12 — uncertainty selection

Add simple selection of the most uncertain examples.

Do not implement this before the core loop works reliably.

# 43. Mandatory development discipline

For every implementation task:

1. inspect the existing relevant code before modifying it;
2. make the smallest change required for the current stage;
3. do not refactor unrelated parts of the program;
4. preserve existing working behavior;
5. add or update tests where practical;
6. run relevant tests;
7. perform a relevant smoke test where possible;
8. inspect failures;
9. fix failures caused by the change;
10. report exactly what changed and what was verified.

A task is not complete merely because code was written.

It is complete only after the relevant checks have been performed or the inability to perform them has been explicitly reported.

---

# 44. Architecture change policy

This document is the architecture specification for automatic landmarking.

Codex must not silently change the architectural decisions defined here.

If implementation reveals that a requirement is incompatible with the existing codebase or would cause significant unnecessary complexity:

1. do not redesign the subsystem automatically;
2. describe the conflict;
3. propose the smallest viable alternative;
4. wait for approval before changing this architecture.

Minor implementation details that do not change responsibilities or persistent data semantics may be chosen freely.

---

# 45. Compatibility with the existing project

Before creating new formats or modules, inspect the existing Morphology Pipeline.

Reuse working components whenever appropriate.

In particular:

* do not replace the current image viewer unnecessarily;
* do not replace working crop handling unnecessarily;
* do not replace working annotation storage unnecessarily;
* do not create duplicate project-state systems;
* do not introduce new dependencies without a clear need;
* do not redesign unrelated morphology functionality.

Auto-landmarking is an extension of the existing pipeline, not a replacement for it.

---

# 46. Resource-saving development policy

Development should minimize unnecessary large-context or exploratory work.

For each task:

* read only the files needed for the requested stage;
* avoid repository-wide refactors unless necessary;
* avoid repeatedly re-reading large unrelated files;
* implement one architectural stage at a time;
* test the changed subsystem before proceeding.

Do not attempt to implement the entire architecture in one task.

---

# 47. Definition of the minimum successful system

The minimum successful auto-landmark subsystem is reached when the following sequence works reliably:

```text
1. manually annotate images
2. train model
3. save model version
4. choose N
5. predict N unlabeled images
6. review predictions
7. correct wrong points
8. convert reviewed images into training-eligible data
9. train a new model
10. compare model quality on validation data
11. repeat
12. predict all remaining images when the user chooses
```

Everything beyond this sequence is secondary.

---

# 48. Primary design priorities

When architectural trade-offs occur, use this priority order:

```text
1. data integrity
2. reproducibility
3. scientific validity of evaluation
4. modularity
5. recoverability
6. usability
7. speed
8. sophistication
```

A simpler implementation that preserves annotations and model history is preferable to a more sophisticated implementation that is difficult to audit.

---

# 49. Non-negotiable rules

The following rules are mandatory:

```text
1. Never train on unchecked PREDICTED annotations.

2. Never silently overwrite MANUAL or REVIEWED annotations.

3. Never overwrite an older successful model.

4. Preserve the model identity that produced every prediction.

5. Preserve original predicted coordinates after human correction.

6. Keep training, inference, evaluation, and GUI logically separated.

7. Evaluate models on data not used to train that model.

8. Keep validation data comparable across model versions where possible.

9. Keep landmark-specific quality metrics, not only one global score.

10. Do not use confidence as a substitute for measured accuracy.

11. Make every large automatic operation recoverable and logged.

12. Do not modify this architecture silently.
```

---

# 50. Final implementation principle

The system is intended to progressively reduce human labor, not remove human control.

The human operator remains the source of verified landmark annotations.

The model provides increasingly accurate proposals.

The workflow therefore remains:

```text
HUMAN
  ↓
MODEL LEARNS
  ↓
MODEL PROPOSES
  ↓
HUMAN VERIFIES
  ↓
MODEL LEARNS FROM VERIFIED DATA
```

This loop is the central design principle of the automatic landmark subsystem.
